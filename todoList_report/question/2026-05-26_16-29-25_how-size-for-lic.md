## Assistant

The `.lic` is a DER-encoded X.509 v3 leaf cert. With the current `CertIssuer` shape, expected size is **≈600-700 bytes** — well under the 1500-byte QR budget the plan sets.

Rough byte breakdown:

| Section | Bytes |
|---|---|
| ASN.1 framing (outer SEQUENCEs) | ~15 |
| Version + 64-bit serial | ~15 |
| Signature algorithm OID (ecdsa-with-SHA256) | ~12 |
| Issuer DN (copied from Leaf CA — depends on CA's CN) | ~50-80 |
| Validity (notBefore + notAfter as UTCTime) | ~32 |
| Subject DN (`CN=<userName>, O=vLearn2`) | ~30-60 |
| Public key SPKI (P-256 named curve) | ~91 |
| Extension `1.3.6.1.4.1.99999.1` machineId (64 hex chars) | ~95 |
| Extension `1.3.6.1.4.1.99999.2` mode (`period`/`permanent`) | ~28-32 |
| Extension `1.3.6.1.4.1.99999.3` days (decimal text) | ~28 |
| Extension keyUsage (digitalSignature, critical) | ~16 |
| ECDSA-SHA256 signature (two INTEGERs) | ~70-72 |
| **Total** | **≈ 480-630** |

Variable factors:
- **User name length** drives the Subject CN.
- **Leaf CA's own CN** drives the Issuer DN — a long CA name eats budget.

Hard ceilings:
- `MainWindow.cpp` warns if the cert exceeds **1500 bytes** ([MainWindow.cpp:194-197](thirdparty/KeyGenerator/src/MainWindow.cpp#L194)) — the practical QR-Code Version 22 / ECC-Medium capacity for binary payload is ~1700 bytes, but we keep headroom for the base64 expansion (1.33×).
- The plan's stated target is **≤ 1 KB** ([docs/0525/17_license_plan.md:22](docs/0525/17_license_plan.md#L22)) — current shape stays well under that for any normal CA + 64-char machine ID + reasonable user name.

If you ever hit the warning, the cheapest savings are: shorten the Leaf CA's CN, or drop the human-readable `O=vLearn2` from the subject.
