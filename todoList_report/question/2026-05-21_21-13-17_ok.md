## How the signing trick works

The signature has to cover the header, but the header itself includes `sig_len` and `sig_offset` which can't be known until after signing. Resolution:

1. Compute the header with `cert_len`/`cert_offset` set, `sig_len`/`sig_offset` **zeroed**.
2. Hash `(this_header ‖ manifest ‖ data ‖ cert)`.
3. Sign the hash → know `sig_len`.
4. Patch the on-disk header with real `sig_len` and `sig_offset = cert_offset + cert_len`.
5. Unpacker re-zeros the same two fields before hashing → same digest → signature verifies.

This is the standard pattern for self-describing signed containers (similar to how Authenticode + APK signing handle it).

## Stage 7 next

Encryption. Per-pack AES-256-GCM with a fresh ephemeral ECDH P-256 keypair:

1. Generate ephemeral keypair `(eph_priv, eph_pub)`.
2. ECDH against the **admin's cert pubkey** → shared secret.
3. HKDF over the shared secret → AES-256 session key + GCM IV base.
4. Encrypt each blob with AES-256-GCM, unique IV per blob (IV_base ‖ blob_index).
5. Embed `eph_pub` (compressed point, 33 bytes) inside the `.ddp` so the unpacker can re-derive.
6. Set `FLAG_ENCRYPTED` in the header.

Flutter side (Stage 8) does the matching: takes the embedded `eph_pub`, ECDH against the admin's pubkey from the embedded cert (same one we used for signing), HKDF, decrypts.
