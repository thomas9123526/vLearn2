# Task 008 — Field-level Encryption for Sensitive DB Columns

## What was done

Implemented transparent AES-256-CBC field-level encryption for sensitive
database columns using an existing transformer in `backend/src/common/field-encryption.ts`.

### Encrypted fields (as of this task)

| Table | Column | Entity field |
|-------|--------|--------------|
| `users` | `name` | `UserEntity.name` |
| `users` | `license_serial` | `UserEntity.license_serial` |
| `users` | `license_machine_id` | `UserEntity.license_machine_id` |
| `vl_user_info` | `email` | `UserInfoEntity.email` |
| `vl_user_info` | `suspended_reason` | `UserInfoEntity.suspended_reason` (added this task) |

### New files
- `backend/src/common/encryption/encrypted-fields.ts` — canonical registry listing all encrypted fields with table/column/entity names.

### Modified files
- `backend/src/database/entities/user-info.entity.ts` — added `encryptedFieldTransformer` to `suspended_reason`.
- `backend/src/admin/admin-users.controller.ts` — fixed email search: uses `encryptField(q)` for exact-match instead of `ILIKE` (partial match is incompatible with AES ciphertext).
- `backend/.env` — added `DB_FIELD_ENCRYPTION_KEY` placeholder (change before production).

### Key: `DB_FIELD_ENCRYPTION_KEY`
Set to any 32-character string (first 32 UTF-8 bytes are used as the AES key).
When absent, the transformer is a no-op so existing deployments boot without it.

### Notes
- Deterministic IV (HMAC-SHA256 of key+plaintext) means UNIQUE indexes remain valid.
- Admin panel email search is exact-match only; name search remains partial (ILIKE).
